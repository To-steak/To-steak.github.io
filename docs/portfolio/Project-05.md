## Abstract

이 프로젝트는 "코딩 에이전트를 활용하면 24시간 안에 목표한 게임을 완성할 수 있는가"라는 질문에서 출발했습니다. 코드는 Claude가, Unity 에디터 작업은 제가 맡는 분업 조건에서 WebGL 액션 타워 디펜스 게임을 3일에 걸쳐 체감 작업 시간 약 24시간 동안 제작했습니다.

Claude는 GitHub에 연결되어 코드 작성, Commit, Push, PR 생성까지 수행했고, 저는 검토와 병합을 맡았습니다. 작업 전 Claude와 함께 프로젝트 설계·코드 컨벤션·개발 로드맵 문서를 작성해 규칙을 고정했습니다.

그 결과 설계 시작부터 약 6.5시간 만에 처음부터 패배까지 플레이 가능한 핵심 게임 루프가 완성되었습니다. 그러나 타워 FBX 적용, Scene 환경 구성, Post-Processing, 시작 화면, UI 연출 등 폴리싱 단계는 완성하지 못했습니다.

체감 작업 시간 24시간 중 설계에 약 2시간, 코드 구현에 약 8시간이 쓰였고, 나머지 약 14시간은 View와 에디터 작업에 쓰였습니다. 병목은 코드가 아니라 사람이 수행하는 에디터 작업, 특히 View와 UI 작업이었습니다. 또한 설계 문서의 분량과 잦은 수정이 에이전트의 토큰을 크게 소모했습니다.

결론적으로 24시간 내 완성은 조건부로 가능합니다. 그 조건은 에디터 반복 작업과 UI 작업을 단축할 수단을 미리 확보하는 것, 그리고 에이전트에게 제공하는 문서를 가볍게 유지하는 것입니다.

## Preliminary

2023년 이후 작더라도 끝까지 완성한 프로젝트가 없었습니다. 취업 준비를 하며 "기간을 24시간으로 짧게 잡고 코드를 Claude에게 맡기면, 작더라도 게임 하나를 완성할 수 있을까?"라는 의문이 생겼고, 이를 직접 확인해 보기로 했습니다. 시작 시점의 Unity 경험은 대학 수업에서 다뤄 본 수준이었습니다.

평소 ECS(Entity Component System)에 관심이 있었습니다. 이전 실험인 [ECS 100k Projectile](/portfolio/ECS-100k-Projectile)에서는 Unity ECS로 발사체 10만 개와 피격체 2,000개의 충돌을 시뮬레이션하며 성능을 측정했습니다.

반면 OOP로 게임을 만들면서는 다른 문제를 느꼈습니다. 이벤트는 흔히 결합도를 낮춘다(decoupling)고 하지만, 실제로 코드를 작성하면서는 드러나지 않는 참조를 만들어 "이 값을 누가, 언제 바꾸는가"를 추적하기 어렵게 했습니다. 진행 중이던 [Project 02](/portfolio/Project-02)에서는 이 문제를 해결하려고 기존 OOP 구조 위에 ECS 규칙을 뒤늦게 적용했습니다.

그래서 이번 프로젝트에서는 처음부터 다음 원칙을 정했습니다.

- ECS 패키지(DOTS)는 도입하지 않는다.
- 상태는 데이터(World), 로직은 상태 없는 정적 함수(System)로 나누는 철학만 순수 C#으로 따른다.
- 이벤트를 금지하고, Logic에서 일어난 일은 기록으로 남겨 View가 읽게 한다.
- 단, UI는 기존 OOP의 MVP 구조를 따르며 이벤트를 허용한다.

이 구조는 LLM과의 협업에서도 의도한 효과가 있었습니다. "게임 상태는 World에서만, 변경은 System의 Tick 안에서만" 일어나므로, Claude가 작성한 코드를 리뷰할 때 확인할 범위가 명확해졌습니다.

플레이어가 히어로를 직접 움직이며 싸우고, 번 골드로 타워를 세우고, 필요할 때 타워에 탑승해 직접 사격하며 기지를 지키는 액션 타워 디펜스입니다. 스테이지는 무한이며, 도달한 웨이브와 적을 처치하면 얻는 점수가 기록이 됩니다.

빌드 타깃은 WebGL로 정했습니다. Unity AI Game Jam에 지원한 뒤 그 연습을 겸한 선택이었고, 이 글을 읽는 사람이 결과물을 바로 플레이해 볼 수 있기 때문입니다.

핵심 루프와 목표 범위는 제가 정했습니다. Claude는 그 안의 세부 규칙을 추론해 제안했고, 저는 이를 확인하며 설계 문서를 확정했습니다.

## Method

### 1. 협업 문서 체계

코드 작성 전에 Claude와 함께 네 개의 문서를 작성해, 세션이 바뀌어도 같은 규칙으로 작업하게 했습니다. 설계가 코드보다 중요하다고 판단해, 계획 단계에서 코드 작성보다 많은 시간을 쓰게 되더라도 감수하기로 했습니다.

| 문서 | 역할 |

| [CLAUDE.md](https://github.com/To-steak/project_05/blob/main/CLAUDE.md) | Claude가 반드시 지킬 아키텍처 규칙과 작업 방식 |

### 2. 작업 흐름

기능 브랜치 하나를 한 세션의 단위로 삼았습니다. 한 기능은 아래 순서로 진행했습니다.

1. 새 세션을 열고 `ROADMAP.md`에서 체크되지 않은 첫 항목을 지정합니다.
2. Claude가 main 최신 브랜치에서 브랜치를 만들어 구현, Commit, Push, PR 생성까지 수행합니다.
3. 제가 GitHub 웹에서 diff를 읽고, 에디터에서 `ROADMAP.md`와 PR 메시지의 "확인 방법"대로 동작을 검증합니다.
4. 필요한 에디터 작업(Prefab, Scene, UI)을 한 뒤 병합하고, 로드맵 체크박스를 갱신합니다.

처음에는 기능을 네 개의 레인으로 나눠 여러 세션을 동시에 진행하려 했습니다. 계획은 2~3개였지만 실제로는 4~5개를 동시에 열었습니다. 그러나 같은 파일과 Scene에서 충돌이 잦아 약 1시간 만에 중단했고, 이후에는 한 번에 브랜치 하나만 여는 순차 진행 방식으로 바꿨습니다. 이 과정에서 PR 두 개를 닫고 도중부터 다시 구현했습니다.

### 3. 단계 구성

| 단계 | 내용 | 비고 |
| --- | --- | --- |
| 준비 | 설계 문서, 폴더 구조, 빈 Scene, WebGL 빌드와 배포 확인 | 배포 경로를 먼저 검증 |
| 기반 | 어셈블리 분리, 코어 루프, 데이터 계약(Component·World·필드·System 껍데기), 베이킹 | 이후 브랜치는 System 내용만 채우도록 계약을 먼저 고정 |
| 기능 | 히어로 이동·전투, 웨이브, 본진(코어), 아이템 드롭·레벨업, Main Scene, 타워, 본진 메뉴 | 이 단계 완료가 핵심 루프 완성 시점 |
| 마무리 | HUD, 오디오, VFX, 애니메이션, 히어로 공격 분리, Scene 칠하기 도구, 밸런싱 | 일부 미완성 |

각 항목에는 "확인 방법"을 함께 두었습니다. 예를 들어 `feat/tower`는 "타워가 적을 막고 부서짐"입니다. 리뷰에서 코드를 모두 읽지 못하더라도, 동작만으로 완료 여부를 판단할 수 있게 하기 위해서였습니다.

### 4. 아키텍처

ECS 패키지 없이 그 철학만 순수 C#으로 설계했습니다.

![한 프레임의 실행 흐름](/images/project-05/uml.svg)

> 한 프레임의 실행 흐름. 입력은 `Update`에서 모으고, 게임 상태는 `FixedUpdate`의 System들이 정해진 순서로 바꾸며, View는 `LateUpdate`에서 그 결과를 읽기만 합니다.

- **World**: 한 판의 모든 상태를 담습니다. 판마다 새로 만듭니다.
- **System**: 상태 없는 정적 함수 모음입니다. 고정 50Hz 주기마다 정해진 순서로 World를 갱신합니다.
- **이벤트 대안**: 이벤트 대신, 그 틱에 일어난 일(피격, 사망, 건설 등)을 값(struct)으로 남깁니다.
- **View System**: `LateUpdate`에서 World와 기록을 읽어 애니메이션, VFX, 사운드, UI에 반영합니다. World를 바꾸지 않고 연출만 합니다.

수치는 모두 Scriptable Object(~Definition)에 두었습니다. 게임 시작 시 이를 구조체로 변환(베이킹)해, System이 Unity 오브젝트를 참조하지 않게 했습니다.

### 5. 에디터 작업

Scriptable Object는 Claude가 만들면서 기본값까지 채워 두어, 이 부분의 에디터 작업은 거의 없었습니다. 시간 대부분은 다음 세 가지 작업에 들었습니다.

1. **Scene 구성**: 부피 1 크기의 지형 FBX를 회전·조합해 원하는 형태의 Scene을 만들어야 했습니다. 코너 옆에는 항상 사이드 길이 붙어야 하는 식의 규칙도 있었습니다.
    - Claude가 처음 제안한 도구는 격자 텍스트로 맵을 적으면 한 번에 생성하는 방식이었습니다. 하지만 규칙과 회전을 텍스트로 표현하기도, 사람이 읽고 이해하기도 어려웠고, 지금 어떤 FBX를 배치하고 있는지 미리 볼 수 없었습니다.
    - 그래서 FBX 썸네일로 타일을 골라 격자에 직접 칠하는 에디터 창으로 다시 만들게 했습니다. 칠한 길을 바탕으로 적 경로와 바닥 Collider도 자동으로 생성됩니다.
2. **UI**: HUD, 메뉴, 설정 등 레이아웃 작업. 단순 반복이지만 양이 많았습니다.
3. **Animator**: 플레이어와 적의 Animator 설정. 역시 단순 반복이었습니다.

![레벨 타일 칠하기 창](/images/project-05/tile_painter.jpg)

> 레벨 타일 칠하기 창. FBX 썸네일로 타일을 골라 격자에 칠하고, 칠한 길에서 적 경로를 자동으로 생성합니다.

![Game 씬](/images/project-05/game_scene.jpg)

> 레벨 타일 칠하기 창으로 만든 Game 씬. 지형 타일을 칠해 여러 갈래의 길이 중앙으로 모이는 맵을 구성했습니다.

## Discussion

### 1. 코드는 Claude에게 맡길 수 있었다

설계 시작부터 약 6.5시간 만에 처음부터 패배까지 플레이 가능한 핵심 루프가 완성되었습니다. 프로젝트 전체에서 Claude가 `CLAUDE.md`의 아키텍처 규칙을 어긴 일은 없었습니다.

리뷰에서 모든 코드를 읽지 못했는데도 큰 문제가 생기지 않은 데에는 ECS 철학을 따른 구조가 한몫했다고 생각합니다. 게임 상태는 World에만 있고 변경은 System의 Tick 안에서만 일어나므로, 확인할 범위가 명확했습니다. 또한 대부분의 동작이 Scene 설정이 아닌 코드에서 결정되는 구조라 에디터 작업 중 사람이 실수할 여지도 적었습니다.

### 2. 병목은 사람 쪽에 있었다

| 구분 | 계획 | 실제(체감) |
| --- | --- | --- |
| 설계 | 8시간 | 약 2시간 |
| 코드 작성 | 5시간 | 약 8시간 |
| View 및 에디터 작업 | 11시간 | 약 14시간 (미완) |

코드는 계획보다 조금 더 걸렸지만 예상 가능한 범위였습니다. 반면 설계를 빠르게 마치고 작업을 시작한 탓인지, 작업 중간마다 설계가 부실한 지점이 드러났습니다. Scene 배치, UI 레이아웃, Animator 설정은 모두 단순 반복 작업이었지만 양이 많았습니다.

### 3. 병렬 세션의 실패

첫날, 작업끼리 영향을 주지 않도록 `ROADMAP.md`를 다시 설계한 뒤 세션 4 ~ 5개에서 서로 다른 기능을 동시에 진행했습니다. 결과는 다음과 같았습니다.

- 사용량이 70%에서 100%로 약 20분 만에 소진되었습니다.
- 핵심 루프가 완성되기 전이라, 서로 독립적으로 나눴다고 생각한 작업도 실제로는 다른 작업이 먼저 끝나야 하는 경우가 여럿이었습니다.
- 실제로 진행된 것은 플레이어 이동뿐이었고, 그마저 다른 세션의 작업과 많은 파일에서 충돌해 되돌리고 다시 만들어야 했습니다(PR #7, #8 재작업).

이후로는 한 번에 브랜치 하나씩 순차로 진행했습니다. 돌이켜 보면 병렬이 애초에 맞지 않는 구조였습니다. 리뷰하는 사람은 저 혼자이므로, 세션을 몇 개 열든 병목은 결국 제 리뷰에서 생깁니다.

### 4. 브랜치 단위가 너무 컸다

기능 하나를 세션 하나, 브랜치 하나로 삼았습니다. 브랜치는 설계 당시 떠오르는 구현 단위로 나눴는데, 그러다 보니 PR 하나의 리뷰 양이 너무 많았습니다. 결국 모든 코드를 읽지 못하고, 핵심만 확인한 뒤 동작하는지 보고 넘어갔습니다.

리뷰 환경도 문제였습니다. GitHub 웹에서 diff를 읽는 것은 가독성이 낮아 피로가 빠르게 쌓였습니다. 브랜치와 커밋을 더 작고 원자적인 단위로 나누면 리뷰 양과 피로를 함께 줄일 수 있을 것입니다.

### 5. 설계와 자원의 불일치

폴리싱 대신 마지막 날에 플레이어 공격 분리와 타워 탑승 시 광역 공격을 먼저 구현했습니다. 게임 설계와 확보한 자원이 맞지 않았기 때문입니다.

- 처음 설계는 클릭 하나로 이동하면서 근거리와 원거리 공격을 모두 자연스럽게 하는 것이었습니다.
- 하지만 이동하며 공격하고, 원거리일 때는 대상을 바라보며 이동하려면 조작을 나누는 등의 다른 조치가 필요했습니다. 24시간 안에는 무리라고 판단했습니다.
- 그래서 원거리 공격을 플레이어 주위를 도는 구체로 분리했습니다. 그런데 구체가 너무 강해서 타워 탑승 기믹의 의미가 사라졌습니다.
- 이를 살리기 위해 타워 탑승 시 광역 공격을 도입했습니다.

폴리싱보다 게임 로직과 재미가 더 중요하다고 판단한 선택이었습니다. Claude가 코드 작업을 했기 때문에 긴 시간이 들지는 않았지만, 그만큼 폴리싱 시간이 줄어든 것은 분명합니다.

### 6. 협업 방식에서 생긴 마찰

Claude는 코드 작성에서 가장 큰 도움이 되었습니다. 하지만 코드에 대해 단순히 질문만 해도, 브랜치를 만들어 Commit, Push, PR 작성까지 한 뒤 확인해 달라고 답하는 경우가 종종 있었습니다. 의문을 해소하려 했을 뿐인데 불필요한 작업이 생겨난 것입니다. 작업 방식 규칙이 강하게 적혀 있다 보니, 질문과 작업 요청을 구분하는 규칙이 따로 필요했습니다. 또한 프로젝트가 커질수록 작업을 마친 뒤 영어로 응답하는 경우가 생겼습니다.

### 7. 문서의 비용

설계 문서는 일관성을 지키는 데 효과가 있었지만 비용도 컸습니다.

- 세션을 시작할 때마다 약 4.4만 자 분량의 문서를 읽게 했습니다.
- 같은 규칙이 `CLAUDE.md`, `DESIGN.md`, `CONVENTIONS.md`, 폴더별 `README.txt` 등 여러 곳에 중복되었습니다.
- 문서를 구현에 맞추는 작업이 계속 생겨, docs 커밋(49개)이 feat 커밋(43개)보다 많았습니다.

### 8. 결론과 다음 실험

24시간 안에 코딩 에이전트로 목표한 게임을 완성하는 것은 조건부로 가능합니다. 코드는 에이전트에게 맡길 수 있지만, 사람이 해야 하는 에디터 작업을 줄일 준비가 없으면 완성까지 가지 못합니다.

다음에 같은 실험을 한다면 아래 순서로 바꿀 것입니다.

1. View 작업을 위한 도구를 먼저 만듭니다. 설계 단계에서 에디터에서 일어날 단순 반복 작업을 미리 예상하고, 그 작업을 줄이는 도구를 계획에 포함합니다.
2. 설계에 최소 5시간을 쓰되, 문서는 가볍게 유지합니다. 중복을 없애고, 세션마다 필요한 부분만 읽게 합니다.
3. Commit, Push, PR을 더 원자적으로 나눕니다. 리뷰가 병목이라는 점을 전제로 작업 단위를 정합니다.
4. 질문과 작업 요청을 구분하는 규칙을 둡니다.
